# 4090A 清理事故后的全评估恢复层裁决

## 裁决

AM-TNC 健康训练继续原进程运行，不重启。训练恢复仍只使用从活动进程删除映射逐字节重建的隔离运行时；统一评估、AM-TNC/ST-CGR 算法裁决与最终交付则使用独立的只读评估运行时。四个仍在等待的评估 child 均已被新监督器原位收养，`restart_count=0`。

## 为什么这样处理

错误清理没有破坏已经驻留内存的 AM-TNC 进程，也没有损坏已完成的 e24 full-state checkpoint。真正的风险是：健康进程一旦退出，原路径已经不能直接提供匹配解释器；同时四个长时间等待的评估进程也仍引用已删除的解释器 inode。直接覆盖或贸然重启会把可恢复的基础设施事故扩大成科学轨迹中断。

因此训练和评估被明确分成两个运行时角色。训练候选复刻活动进程的 111 个删除映射并由原入口 relay 触发；评估候选固定为已经通过 bundle 测试且尚未加载数值模块的统一栈。恢复监督器同时锁定控制源码、命令文件、child checkout commit/clean 状态和解释器，并且只有 child 真正退出且状态仍可恢复时才重新启动。

## 对损失的判断

- 目前没有损失任何已完成训练 epoch，AM-TNC PID 3446758 未被中断，已完成 e24 并进入 e25。
- 若未来 AM-TNC 进程失败，可从最近完整 epoch 的 full-state checkpoint 恢复；最坏预期重做当前未完成 epoch，而不是重跑整条实验。
- GPU 下一步逐位等价没有被夸大声称。隔离运行时、映射哈希、全量测试和 CPU 单更新探针提供了当前可获得的最强恢复证据。
- 评估/交付链的单进程死亡风险已经关闭；旧的四个固定 PID 健康 watcher 已在替代层稳定、脱离 SSH 后安全退休。

## 不变边界

本次只修复工程恢复能力，不改变训练配置、数据顺序、算法实现、matched 关系或评估协议；没有读取性能值，confirmation20 继续封存。
