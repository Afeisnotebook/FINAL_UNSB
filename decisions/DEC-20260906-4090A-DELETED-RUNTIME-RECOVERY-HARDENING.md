# DEC-20260906：4090A已删除运行时的隔离恢复加固

## 结论

4090A 的错误清理没有造成已经完成的 AM-TNC checkpoint 丢失，训练 PID 3446758 也始终没有被中断或重启；但此前将新建的 `unsb_cov` 目录称为“精确核心运行时恢复”是不成立的。活进程解释器与重建解释器哈希不同，活进程实际加载的 NumPy/Pillow 分别是 2.2.6/12.2.0，而重建目录是 2.1.3/11.3.0。两者混合会在隔离导入时直接失败。因此，本裁决只覆盖并撤回上一裁决中的“未来恢复环境已经精确完成”字段，不覆盖其中已经独立验证的动态论文交付链健康状态。

## 已采取的非破坏性措施

- 从活 PID 的 `/proc` 映射中逐文件保全 111 个已经删除的二进制和共享库，共 4,198,514,872 bytes；活训练未收到 signal。
- 在 `/home/yc/recovery_snapshots` 内构造新的隔离运行时。活进程映射的 111 个文件在候选中全部存在且逐字节相同；解释器、NumPy、Pillow 与 Torch 关键原生库均由哈希绑定。
- 新候选通过核心包、LPIPS/Clean-FID 导入，冻结训练 checkout 的完整测试结果为 379 passed、1 skipped，并能从 e24 完整状态在 CPU 隔离副本中加载后继续一个真实 optimizer update。
- 现有 AM-TNC supervisor 把未来重启命令固定为原 `unsb_cov/bin/python`。在隔离门通过后，三个标准 Python 入口已原子替换为只负责 `exec` 新候选的 relay；旧重建二进制另存快照。这样不改变仍在运行的 supervisor/trainer，却避免 child 将来退出后被错误的 2.1.3/11.3.0 环境重启。

## 损失与边界

当前 e24 完整状态已经哈希闭环，因此已经完成的科学状态没有损失。若活进程继续健康，原训练连续运行到 e200；若之后发生真实工程退出，supervisor 会从最近完整 data epoch 使用新隔离运行时恢复，最多损失当前未完成 epoch 的计算时间。
